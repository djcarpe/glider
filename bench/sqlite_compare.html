Glider vs SQLite

Every query is written once in glider's Cypher and once in hand-written SQL against a normalized schema with foreign keys and indexes, run on the same graph, and checked row for row. Pick a dataset size below, then open a row to see both queries, their answers and SQLite's plan.

How this was measured
  • Data. scale-gen writes a deterministic graph (people, companies, products, orders, documents, a category tree, an event chain) with 16 relationship types: power-law hubs, communities, bipartite, multi-edges, dense cliques, trees, a DAG, a long chain and self-loops. The size names the generator's target; each engine's on-disk size is shown per tab.
  • SQLite schema. One table per label, one table per relationship type with FOREIGN KEYs to its end tables and (src, dst) + (dst, src) indexes, plus the same property indexes glider keeps: Person email / age / country, Order ref, Product sku, Event seq. Loaded from glider export, then indexed, PRAGMA foreign_key_checked and ANALYZEd. MENTIONS points at three tables, so it carries a kind column instead of a foreign key.
  • Timing. Both engines are timed inside the process running the query: glider by its shell's .timer, SQLite around execute + fetchall in Python's sqlite3. Cold is the first run in a fresh process after evicting the files from the OS page cache; warm is the median of the next five. Both use a 1 GiB page cache.
  • Answers. Rows are compared after normalizing numbers; unordered results are compared as sets. BFS compares (id, depth) sets; shortest path compares hop counts.
  • Machine. 8 cores, 31 GiB RAM, NVMe, Linux. Each process ran under a 12 GiB address-space cap.
