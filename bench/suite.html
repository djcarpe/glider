Glider vs SQLite vs Memgraph

The same graph in three engines: glider as a property graph on disk, SQLite as a normalized schema with foreign keys and indexes, and Memgraph, an in-memory graph database. Every read and algorithm is written for each engine and checked against glider's answer. How this was measured
  • Data. scale-gen writes a deterministic graph: people, companies, products, orders, documents, a category tree and an event chain, with 16 relationship types covering power-law hubs, communities, bipartite, multi-edges, cliques, trees, a DAG, a long chain and self-loops. The size names the generator's target; each engine's on-disk size is in its tab.
  • SQLite schema. A table per label and per relationship type, FOREIGN KEYs to each end, (src, dst) and (dst, src) indexes on every relationship table, and glider's property indexes (Person email / age / country, Order ref, Product sku, Event seq). Built from glider export, indexed, foreign_key_checked and ANALYZEd; WAL mode, synchronous=NORMAL (FULL for the fsync workload), 1 GiB page cache.
  • Timing. Inside each engine's process: glider's shell .timer, SQLite around execute + fetchall in a Python worker. Cold is the first run in a fresh process after evicting both files from the OS page cache; warm is the median of the next five. Anything slower than 20 s ran once.
  • Algorithms. glider's built-in CALLs against hand-written SQL doing the same thing: PageRank with glider's formula (all nodes, dangling mass shared evenly, five iterations), connected components by minimum-label propagation, degree by GROUP BY, BFS and shortest path by recursive CTEs. Answers are checked; PageRank to a relative 1e-6.
  • Writes. The same operations through each engine's query language, run last because they change the data. Glider sync normal against SQLite synchronous=NORMAL; the fsync row is glider always against SQLite FULL. Afterwards both engines' Person and KNOWS counts must agree.
  • Profiles. Grafana Alloy samples both processes with eBPF at 97 Hz. glider runs as its profiling build (release plus symbols and frame pointers). After its timed runs each read repeats for 1.5 s, so even microsecond queries have a flamegraph.
  • Memgraph. memgraph/memgraph-mage 3.13 in Docker, capped at 24 GB. Each size is regenerated fresh, split into CSV and bulk-loaded with LOAD CSV (analytical mode, then transactional), with a gid property carrying glider's id and the same indexes. Queries are glider's Cypher with glider-only syntax translated (id(x) to x.gid, CALL bfs and shortestpath to Memgraph's *BFS expansions, the algorithms through MAGE on the KNOWS subgraph). Times are Memgraph's own parse + plan + execution from the query summary; writes use parameters, as SQLite does, and autocommit writes are timed from the client because the commit is not in the summary. Memgraph holds the whole graph in RAM, so sizes that do not fit are marked instead of run. The first read after loading is Memgraph's "cold": its data never leaves memory.
  • Machine. 8 cores, 31 GiB RAM, NVMe, Linux; each process under a 12 GiB address-space cap.
