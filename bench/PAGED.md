# glider on paged storage: 1, 5, 10 and 25 GiB

Generated by `bench/paged_scale.py`, rendered by `bench/paged_report.py`. The graphs come from `scale-gen` with the same generator and seed as the snapshot-image run in [`SCALE.md`](SCALE.md), so every number here has a counterpart there: same nodes, edges, properties and queries. Each glider process ran under a 16 GiB address-space cap on a machine with 31 GiB of RAM. **cache 1 GiB** is the default configuration; **cache 64 MiB** adds `--cache-size 64M --work-mem 64M`, to show what a small memory budget costs. "Cold" means the files were evicted from the OS page cache first. Times are wall clock; memory is peak RSS unless stated.

| size | nodes | edges | paged database | snapshot image (old) | paged bulk load (time · RSS) | image build, old (time · RSS) |
|---|---|---|---|---|---|---|
| 1GiB | 1,247,371 | 8,027,661 | 1.39 GiB | 1.00 GiB | 19.30 s · 555 MB | 9.47 s · 406 MB |
| 5GiB | 6,237,595 | 40,209,610 | 7.02 GiB | 5.00 GiB | 1.6 min · 542 MB | 46.05 s · 1.77 GB |

The 1 GiB graph built through the transactional API instead (every node and edge an `add_node` / `add_edge` through the write-ahead log): 2.0 min · 290 MB, 2.16 GiB.

The bulk load sorts everything externally within its working memory and builds each B+tree bottom up, so its memory does not grow with the graph; the old image builder kept a few integers per node and edge in RAM. The paged file is larger: one B+tree entry per edge endpoint, plus page slack (see PAGED-1 in `docs/TODO.md`).

## Crash recovery and checkpoints

| size | log left by kill -9 | reopen: replay (time · RSS) | verify after | checkpoint | old engine COMPACT (time · RSS) |
|---|---|---|---|---|---|
| 1GiB | 7.2 MiB | 312 ms · 18 MB | ok | 10.3 MiB in 11.0 ms | 7.88 s · 901 MB |
| 5GiB | — | — | — | — | 42.49 s · 4.09 GB |

A writer running a stream of autocommit statements with checkpoints off is killed with SIGKILL; the next open replays the committed log and a full `verify` follows. A checkpoint writes only the pages changed since the last one, where the old engine's compaction rewrote the whole file.

## `:memory:` with a limit

`pagebench memfill --max-mb 256` inserts until the graph is full: after 1,138,000 committed entries the next write failed with "graph is full: 257.0 MiB in use, max_memory is 256.0 MiB", was rolled back, and the graph stayed readable and writable (deletes, then more inserts) — 1.13 s, peak RSS 390 MB.
